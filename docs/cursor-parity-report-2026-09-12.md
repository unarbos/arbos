# Cursor parity report, 2026-09-12

First gap report of the parity process (see `cursor-parity-process.md`). It compares Cursor's Agents Window with the Arbos desktop app on branch `rust` as it was on 2026-09-12, prompt by prompt and aspect by aspect.

## Sign-in status: blocked

Cursor desktop was installed on the VM (Linux AppImage, display `:1`) and reaches the Agents Window, but only up to its login wall. Signing in needs a browser session on cursor.com; the app does not accept `CURSOR_API_KEY`, and no 1Password item in the Arbos vault holds a Cursor session. Evidence: `media/parity/cursor/vm-00-keyring-dialog.png`, `vm-01-login-wall-editor-window.png`, `vm-02-browser-sign-in-page.png`, `vm-03-command-palette-agents-commands.png`, `vm-04-agents-window-login-wall.png`, `vm-agents-window-login-wall.mp4`.

What Jacob has to do, either option:

1. **Device link.** Run `bash internal/parity/cursor-login-link.sh` on the VM while the app is up. It clicks "Log In", copies the one-time link (`https://cursor.com/loginDeepControl?challenge=…&uuid=…`) to `/tmp/cursor-login-url.txt`. Open that link in a signed-in browser. The app on the VM polls until the link is used, then it is signed in. The link only works while that app instance is still waiting.
2. **[from memory]** Copy the session from a signed-in machine: the token lives in Cursor's local state store under the user config directory; copying it into the VM's Cursor config would sign the VM in without a browser. Not tested.

Until one of these happens, the Cursor side of every row below rests on **public material**: frames from Cursor's Projects launch video (`public-video-frame-*.png`), the changelog clips (`public-changelog-projects-*.mp4`) and the docs pages (`public-docs-*.png`). These are real screens of the product but not our prompts, so timings and text differ from the Arbos side.
