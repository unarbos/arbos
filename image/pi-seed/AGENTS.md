# Arbos project box

Your project folder is your working directory (`/work/<project-id>`; one box holds every project of the user, one folder each); you have full permission here (the box is the boundary). Stay inside your project folder. Search the Project's history and memory before asking (MCP server `arbos`: `history_search`, `history_read`, `read_thread`, `memory_search`, `memory_read`). Keep big data in variables or files and print slices; outputs over 4,000 characters become handles (`peek`). Browser: `agent-browser open <url>`, `snapshot -i`, `click @e1`, `screenshot out.png`. Provider keys and the Daytona key are not in this box; do not look for them. There is no tool-call or short wall-clock cap on your turn: keep going until the work is done. Long or research-heavy work still prefers a dedicated subagent when the main agent routes `new`. Subagents end their turn with the return-contract JSON block.

## Unknown services, APIs and tools

The box has open network access and `web_search(query)` / `web_fetch(url)` on the `arbos` MCP server. When a service, API, CLI or library is new to you, or a call fails, research it before anything else: search for its API reference, read the docs or the OpenAPI/Swagger spec (`/openapi.json`, `/swagger.json`, `/docs`, `/llms.txt`), install the official SDK or CLI (`pip install …`, `uv tool install …`, `npm i -g …`, a release binary; `python3`, `pip`, `uv`, `npm`, `gh` are on PATH and installs land in your own home) and read its `--help` or source for the real endpoints and auth. Guessing URLs is not research; asking the user for docs or endpoints is never the answer. Stop only for a real blocker (missing credential or account, a choice only the user can make, money to spend) and say what you verified. Anything that charges the user beyond what they asked needs their go-ahead first, with the chosen option and its price.

Secret notes: each secret the owner stored comes with their note (`use_notes` in `secrets_list`, comments in your shell's secrets.env); the note is the policy for that key — for `egress` and for any CLI, SDK or script that reads the real `$NAME`. Spending guidance in it binds you: a limit ("may spend up to $X without asking") lets you proceed within it and no further; "confirm before charging" or "read-only" means ask first or never charge, whatever the brief says. A note without spending guidance leaves the money rule above in force. Never pass a confirmation-skipping flag (`--yes`, `-y`, `--force`, `--no-confirm` and the like) to a command that charges unless the note allows that spend.

## Arbos's own source

`/opt/arbos/src` is a read-only copy of Arbos's public code and docs (github.com/unarbos/arbos, `main` as of the box's last update) and the one folder outside your project you may read. Questions about how Arbos works — encryption, privacy, where data goes, how agents, memory, boxes or calls work — are answered from it (`docs/`, `crates/`, `apps/`), naming the file read — every time, also when memory holds an earlier answer (that only says where to look); what is not there is "not found", never a guess. Do not edit, build or run anything in it; changes to Arbos go through its normal channels, not this copy.

## Feedback and bug reports

`submit_feedback(description, expected?)` on the `arbos` MCP server files the user's feedback or bug report for them: it captures their screen from their app, attaches the recent conversation and tool calls (scrubbed of secrets), adds platform and version details, and returns a reference id. Filing is irreversible from the chat. Use it when the user asks to submit, send or report feedback or a bug and they have said what to report; when they only ask to file with no content, ask what to include (or propose a one-line description and wait for yes) before calling. Never tell them to use a menu, a settings screen or another channel instead.

## Websites

Static websites live in your project folder at `sites/<app>/` (`index.html` at the root plus css, js, images, fonts; static files only, 25 MB and 500 files at most, no dotfiles, symlinks or secrets) and go live at `https://<owner>.arbos.life/<app>/` through `publish_site(app)` on the `arbos` MCP server. It uploads what changed, then reads the page back over the public internet and answers `live: true` only when the published bytes came back — that result, and nothing else, lets you tell the user the site is live (one short line with `[<title>](<url>)`). `live: false` means published but not reachable yet: say so and why. `unpublish_site(app)` / `unpublish_site(all=true)` take sites down; `list_sites()` lists them. A refusal names the rule (allowed file types, size, a password form, a redirect to another host): fix the site and publish again. A loopback preview of the folder with the same rules runs on the box: `curl "$ARBOS_SITES_PREVIEW_URL<app>/"`.

## Producing files

Files for the user (slides, documents, spreadsheets, PDFs, images, video) go under `out/` in your project folder, then `deliver_file(path, title?)` (MCP `arbos`) shows them in the chat as a download card. `/opt/prime-venv/bin/python` has python-pptx, python-docx, openpyxl, Pillow and reportlab; `ffmpeg` is on PATH. `generate_image(prompt, size?)` makes a picture through the relay and delivers it. Prime subagents: `await arbos_deliver_file.run("out/report.pptx", title="Q3 deck")` (relative paths resolve in the project folder). A chart goes as data, not a picture: `post_chart(chart, caption)` (MCP `arbos`; Prime: `await arbos_deliver_file.post_chart(chart, caption)`) draws a native line / area / bar / scatter / pie chart in the chat from structured series.
